# Independent TanStack architecture review

Reviewed README, maintained routes, shared React/data modules, build/dev/serve bridges, templates and generated client route wiring. I did not read the implementation conversation or existing evaluation conclusions. This is chiefly source evidence: local HTTP probes to ports 4202/4203 failed to connect in this reviewer environment, and `bun run check` could not run because `bun` was absent from its PATH. Consequently I do not claim browser hydration, production status codes, or successful type checking were independently verified.

## Overall assessment

The interactive hybrid application is recognizably TanStack Start, not a static imitation or a custom replacement router. Its integration boundary is sensible for public, maintained Markdown beside a client-interactive workspace. I found no source evidence that the hybrid disables application SSR, Query hydration, server functions, or Router transitions between app pages. The strongest limitation is that documentation is intentionally outside the application runtime; claims of equivalent capabilities must qualify that difference.

## Strengths and supported conventions

- Both routers create a fresh QueryClient inside `getRouter`, expose it through typed route context, and call `setupRouterSsrQueryIntegration`. Route loaders call `ensureQueryData` with the same query options consumed by `useSuspenseQuery`. This follows the [official Query integration](https://tanstack.com/start/latest/docs/framework/react/guide/tanstack-query), including isolation between requests and the supported hydration integration. A 30-second stale time avoids a needless immediate successful-data refetch.
- File routes use `createFileRoute`; root documents use `HeadContent`, `Scripts` and `Outlet`; application navigation uses Router `Link`; fixture access uses Start `createServerFn`. The Vite plugin precedes the React plugin. There is no bespoke app renderer or manual hydration serialization in the maintained source.
- The control is a legitimate static-publication baseline: it uses Start's own configured prerender pages for the landing page and all 60 doc slugs, rather than making every document incur runtime SSR. Explicit pages and disabled discovery/crawling are supported [prerender configuration](https://tanstack.com/start/latest/docs/framework/react/guide/static-prerendering). Its SSR-only alternative is correctly identified as a different workload.
- Shared fixtures, Query options, app views, styles, lockfile and near-identical app routes substantially reduce confounding. The server adapter delegates unmatched requests to the built Start handler; it does not implement server functions itself.

## Concrete defects and weaknesses

1. **Shared missing deployment handling is a soft not-found.** `shared/Portal.tsx` displays “Deployment not found” inside a successfully loaded deployment route. Neither detail loader validates the ID nor throws Router `notFound()`. Inference from this code: missing IDs receive normal successful route semantics rather than an actual 404, unlike the control doc route, which explicitly throws `notFound()`. Validate the deployment in the loader and throw `notFound()` in both apps. This is a shared defect, not hybrid damage; HTTP status was not independently measured.
2. **Saved theme is not reapplied after reload.** Settings loads stored `theme` into React state, but writes `document.documentElement.dataset.theme` only on submit. The root document has no saved-theme initialization. Thus a saved light preference is selected in the form after reload while the rendered page retains the default dark styling until saved again. This follows directly from the source; browser reproduction was unavailable. Apply the preference centrally at application initialization, with an explicit hydration-safe strategy.
3. **Development document additions/deletions are incompletely watched.** `tools/dev-plugin.ts` listens only for `change`, not `add` or `unlink`. Changing `docs/index.json` will normally trigger regeneration, so the documented add-to-index workflow mitigates this, but deleting or creating an indexed source after an earlier metadata save does not reliably rebuild. Register all relevant watcher events and handle bursts in one rebuild.
4. **The app fingerprint omits build-affecting tooling inputs.** `tools/build.ts` hashes app/shared/static sources, Vite config, package manifest and lockfile, but not `tsconfig.json` or the imported `tools/dev-plugin.ts`/`tools/sync-docs.ts`. A configuration/plugin change can therefore leave a reused Vite output that a clean build would change. The plugin is currently mainly a development concern, so this is a conservative invalidation weakness rather than demonstrated stale production behavior. Hash the actual relevant config/plugin dependency closure, or narrow and document precisely which files require `build:full`.
5. **The control understates seamless navigation on important entry links.** `Header` uses ordinary anchors for home and docs in both apps, and `Landing` uses anchors for its calls to action. In the control those destinations are Router-owned and can use client transitions, but these links reload the document. Its documentation sidebar does use `Link`, so client doc transitions are retained there. This is a visible fairness limitation if navigation speed or retained state is compared; provide Router links in the control's shell or explicitly measure both full-page and client-transition paths.

## Natural and forced boundaries

Natural: Markdown publication has no fixture dependency and does not require React state. Ordinary anchors across `/docs/*` and `/app/*`, plus standard Start routes inside `/app/*`, are an understandable ownership boundary. Nift's template/dependency model has a plausible independent role here.

Forced by the comparison: there are two document renderers (Nift markup versus marked), two shell implementations (templates versus React), derived wrapper/tracking/navigation files, a custom Vite middleware, fingerprint orchestration, and a local static-first hosting adapter. These are real maintenance costs, even though each is small. They should count against any saved app rebuild time. Shared CSS/data does not eliminate shell drift or differences in Markdown dialect/escaping.

Lost hybrid documentation capabilities are actual tradeoffs: no React hydration, Router preloading/client navigation between documents, or React-held state shared across docs and app. Returning from a doc creates a fresh app runtime and Query cache. The current app relies only on fixtures and explicit localStorage preferences, so source review does not reveal an essential app feature requiring that continuity. A future authenticated or personalized documentation surface would make the boundary substantially less natural.

## Practical improvements and evaluation limits

Keep the ordinary TanStack application architecture. Fix shared not-found and preference behavior, tighten invalidation/watch coverage, and make the control navigation comparison explicit. Track template/React shell duplication and adapter code as integration overhead. Separate cold build, warm no-op build, one-Markdown-edit build, and shared-shell-edit build: a hybrid cache hit versus a mandatory full control rebuild is useful workflow evidence but is not an apples-to-apples compiler-throughput result.

Production packaging currently assumes that control docs remain readable at the build-machine absolute `__CORPUS_ROOT__` for runtime doc server functions. The local experiment satisfies that arrangement, but a relocated deployment of only `control/dist` would lose client doc loading. This is a packaging limitation, not an observed local failure. Include docs in a deployment artifact or compile server-side Markdown assets if portability becomes part of scope.

This review does not establish byte-for-byte Markdown output parity, missing-document HTTP behavior, error-boundary UX, browser hydration correctness, or real API/mutation/authentication behavior. The fixture-only server function is a credible supported data-access demonstration, but cannot substantiate broader full-stack production claims.
