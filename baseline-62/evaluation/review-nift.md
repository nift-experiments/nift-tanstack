# Independent Nift integration review

Reviewed the README, maintained templates/content, sync/build/dev/serve tooling, generated tracked metadata and representative Nift dependency sidecars. Installed executable reports Nift v4.12.0. This is a source-and-artifact review; no source edits, rebuilds or mutation tests were performed. HTTP connection to 127.0.0.1:4202 failed from this review process, so browser/runtime behavior is not independently verified here.

## Verified strengths

- This uses Nift's actual rendering and dependency model. `content/docs/start/workspace-setup/index.html` is a tiny `@markup(md, 'docs/start/workspace-setup.md')` wrapper, rather than pre-rendered HTML supplied by a competing Markdown pipeline. Its `.nift/public/docs/start/workspace-setup/index.info.json` lists the original Markdown, wrapper, docs template and both generated includes as dependencies. This is direct artifact evidence of native Markdown tracking, though not a mutation-test result.
- Templates and generated navigation use `@path` for managed docs, landing and CSS paths. The representative sidecar records the resulting output requirements; generated links can be validated through Nift. `/app` links intentionally cross to Start. The explicit split is sensible for a documentation-heavy application where static docs are acceptable.
- Generated navigation/wrappers use write-if-changed. This preserves useful modification times for native incremental work. Maintained templates and landing content are no longer rewritten by the adapter.
- The app remains a standard Start/Vite application. There is no second app compiler or hand-rendered substitute for Start server functions. The shared application source makes the experiment more credible than two separately implemented dashboards.
- Retirement cleanup targets actual `page.name + '.html'` paths; current names include `/index`, so this matches the generated directory-index layout.

## Concrete integration weaknesses

1. **The app fingerprint is not a complete build-input key.** `tools/build.ts:5` includes src/shared/static, Vite config, package manifest and lock, but omits `tsconfig.json` and `tools/dev-plugin.ts`, which the Vite configuration directly imports. A changed TypeScript path/compiler setting or imported plugin implementation can therefore retain the previous app bundle on ordinary build. Fingerprinting every shared file is conservative in another direction: control-only `shared/Docs.tsx` also rebuilds the hybrid app. Separate correctness-critical dependencies from harmless over-invalidation.
2. **The cache-hit check proves too little.** `tools/build.ts:7` checks only the fingerprint and `dist/server/server.js`. Deleting or partially restoring `dist/client` while retaining that server file can skip Vite with missing app JS/CSS. The hash does not include the executable runtime/toolchain or build-affecting environment either. These are code-established invalidation gaps; their failures have not been induced here. Use a successful-build manifest with required client/server outputs and explicit environment/tool versions, or simplify to an explicit docs-only command plus ordinary Vite build until a robust cache is worthwhile.
3. **Dev content discovery and metadata freshness are incomplete.** `tools/dev-plugin.ts:5` subscribes only to `change`, so ordinary add/unlink events do not schedule publication. `sync-docs.ts:2-3` imports metadata once; the long-lived Vite process can see a JSON change event yet regenerate navigation/tracking from its original module values. Production invocations start fresh, so this is particularly a dev issue. Read metadata within `syncDocs`, watch add/change/unlink, and validate unique slugs/pages, section membership and referenced files.
4. **Dev watch/build lifecycle is fragile.** The plugin watches `content`, including generated wrappers written by its own sync stage, allowing a metadata update to schedule redundant builds. The debounce does not serialize the asynchronous sync/build jobs, and `spawnSync` blocks Vite's event loop during Nift work. There is no close cleanup for its timer/listener. These are verified implementation properties; actual duplicate-run/race frequency is unmeasured. Use an async child process, a single-flight queue with one pending rerun, and exclude generated wrappers from input events.
5. **The declared derived boundary is not reproducible from maintained inputs alone.** `sync-docs.ts:9` unconditionally reads `.nift/tracked.json`, although the README calls that file derived. Removing that generated file prevents regeneration. Preserve maintained `.nift/config.json`, allow missing tracking to mean an empty previous set, and keep the prior-output manifest separately if deletion cleanup needs it. Test a clean-derived build and a removed-page build.
6. **Two navigation/landing implementations can drift.** The static landing is maintained HTML with explicit section links while the control landing maps `site.sections`; header markup is also duplicated between React and sync generation. This is acceptable experimental scaffolding but real maintenance overhead. A changed first guide or section order may alter only one version. Add a small structural parity check or choose a neutral shared content model for landing text/cards; do not introduce a third renderer merely to deduplicate a little markup.

## Necessary stages and avoidable work

The split genuinely needs Start compilation and Nift publication. The metadata-to-wrapper bridge also currently has a reason: one maintained corpus and one metadata index must produce Nift tracked pages. It is small enough to justify, but is custom orchestration users must own. Every normal invocation walks/hashes the entire app input set, copies CSS unconditionally, reads/checks every wrapper and starts Nift. Consequently 'Markdown skips Vite' is a narrower and defensible claim than 'only the changed page does work'. The global sidebar naturally makes metadata/navigation changes fan out across all docs; this is desired dependency behavior, not a native incremental defect. CSS is copied both to Nift public output and by Vite; write-if-changed would avoid a needless static-output timestamp change.

The default initialized `templates/template.html`, `templates/head.html` and `public/assets/*` are not selected by current tracked pages. They appear to be residual scaffold rather than useful architecture; confirm no intended usage and remove in a later cleanup. A full app/compiler abstraction would add complexity without benefit.

## Capability limits and evaluation implications

Nift contributes static HTML publication and native dependency/path tracking here. It does not supply a supported TanStack integration in this experiment: the dev middleware, route ownership, combined serving, metadata adaptation and app caching are bespoke. This review does not establish whether such an integration exists elsewhere. A reusable integration would need output manifests, watch lifecycle handling, clean-build/retirement behavior, cross-boundary URL tests and clear deployment guidance.

Static docs have no React hydration or Router transitions. Navigation resets the document and any in-memory application state when crossing the boundary. Those are deliberate capability differences, not equal-work performance wins. Likewise the local custom Bun server is enough for evaluation but does not establish production hosting, cache headers or base-path deployment support. Hard-coded `/app` and React root links currently assume deployment at the origin root even though managed Nift paths are relative.

No claim about end-to-end incremental correctness, watch reliability or measured performance should rest on this source review alone. The most valuable next verification is a small isolated matrix: clean-derived build; unchanged build; one Markdown edit; template/include edit; metadata addition/removal/rename in an already running dev server; tsconfig/config dependency edit; and missing-client-output recovery. Assert exact output content and absence of retired pages as well as build timings.
