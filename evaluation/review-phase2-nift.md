# Independent Phase 2 Nift review

This is a read-only source review of Phase 2 and the preserved Phase 1 Nift review and summary. No build, browser session, deletion, failure injection or timestamp mutation was performed by this reviewer. The parent evaluation runs the browser and benchmark campaign separately; its results should accompany this report. Code-established properties below are distinguished from predicted failures. The initial 500-page prototype timings are explicitly unmatched and support no speed comparison.

## Assessment

Phase 2 is a much fairer test of Nift's incremental planner than Phase 1. Both models now use the same Router/Start/React shell, MDX compiler, payload format, search implementation, two compiler workers and two bounded SSR workers. Both cache the application bundle and individual documents. Nift genuinely performs dirty-page discovery and native publication; it does not perform the MDX compilation or HTML SSR. The architecture's most valuable improvement—content edits no longer requiring an application rebuild—is also available to the control, so it cannot be attributed to Nift.

On source evidence alone I would retain the simpler control for a new portal. Nift is worth adopting here if the matched campaign demonstrates a material planner benefit, or if an existing Nift project already benefits from its dependency graph and native diagnostics. No crossover scale or performance win is established by this review. The preserved 62-page verdict remains a historical result for its original architecture, not a verdict on this new implementation.

## Verified strengths

- `tools/dirty.n` invokes native `status().stringify()`. `tools/build.ts` maps returned slugs to compilation jobs, then calls `nift build`. Generated wrappers declare original-source, compiler-key and metadata dependencies and publish the compiled JSON through tracked `inject(...).stringify()`. `hybrid/templates/payload.html` is simply `@content`. This is real Nift dependency/publication integration, although the payload is produced externally.
- Metadata includes previous/next navigation before keys and wrappers are generated. A reordered or renamed neighbor therefore invalidates affected payloads in either model. All active records are freshly read for every invocation, avoiding Phase 1's long-lived metadata import issue.
- Write-if-changed preserves wrapper, metadata and compiler-key timestamps. The compiler key includes the worker source and dependency lock. Control content keys include source bytes, metadata and compiler key. Shared React components are runtime provider components, so their edits invalidate the app/SSR rather than recompiling every MDX document.
- The application cache now includes `tsconfig.json`, package/lock, shared source, runtime versions, `NODE_OPTIONS` and `VITE_*` environment. A manifest checks existence of recorded client and server assets. This substantially improves Phase 1's single-server-file check.
- Document data stays outside the application bundle, and SSR reads current published payloads. Shared shell and React links remove Phase 1's separate static-doc navigation boundary at the implementation level. Actual state preservation and hydration still need browser evidence.
- Dev tooling observes add/change/unlink under the corpus and serializes content builds with a pending rerun. It reports child errors through Vite and removes its listener/timer on disposal. These directly address several Phase 1 concerns.
- Deleted tracked records trigger removal of payload JSON, distributed content JSON and directory-index HTML based on the previous content manifest. The server validates document slugs and checks path containment.

## Concrete weaknesses and predicted consequences

1. **The planner comparison uses different correctness semantics.** `.nift/config.json` selects `incremental-mode: modified`; control compares SHA-256 content keys. Local Nift source (`nift/src/ProjectInfo.cpp`, `dependency_changed` and its prepared identity path) confirms modified mode checks dependency timestamp against page metadata. The wrapper still hashes every source for control-style downstream keys, but hybrid compilation selection ignores a changed content hash unless native status is dirty. A byte edit preserving an old mtime can therefore leave hybrid payload code stale while recording a new content key and rebuilding search/SSR from the stale payload. This is a source-derived failure hypothesis, not an induced failure. Include a preserved-mtime edit test, and compare Nift hash/hybrid mode or document the timestamp contract explicitly.

2. **Successful-stage keys can be committed ahead of publication completion.** `content-keys.json` is written before copying selected payloads into `dist/content`. If a copy fails while an old destination exists, a retry can select zero documents and skip replacing that old destination. Search consumes cache payloads while SSR consumes distributed payloads, so they can disagree. Deletion cleanup likewise runs before the manifest commit: an interrupted later copy can leave old served content with current keys. Use a separate distribution key per payload or stage outputs and commit a successful-publication manifest last. The operation ordering is verified; the failure outcome is inferred.

3. **Incremental keys omit some maintained build logic.** The Vite config directly imports `tools/dev-plugin.ts`, but `appInputs` does not include it. `tools/render-worker.ts` is absent from render keys. Search options and indexing logic inside `tools/build.ts` are absent from `searchKey`, which hashes only content keys. Editing these implementations can retain previous generated outputs on an ordinary invocation. Add explicit stage implementation/version keys and include imported config helpers. The plugin omission is mainly a cache completeness issue here because its production behavior is limited; the renderer/search omissions directly affect generated artifacts.

4. **Recovery checks establish existence, not integrity.** Existing corrupted/truncated payload JSON or JS/CSS can be accepted. Missing compiled intermediates are also different from missing published payloads: hybrid selection explicitly checks published payload size, while Nift's injected dependency should detect a missing compiled file. A complete interruption/corruption matrix is needed before claiming robust cache recovery. Writes and copies are direct rather than atomic; `run()` does propagate nonzero child status, but that does not make the whole pipeline transactional.

5. **Search is cached, not incrementally updated.** A content-key change reconstructs MiniSearch from every active payload, serializes one global index, and later loads it fully in the browser. This is identical across models and will increasingly limit one-document rebuild and search startup as scale grows. The extracted text is a regex-cleaned source prefix capped at 18,000 characters, not rendered semantic text; later content can be unsearchable. These are verified implementation choices, not measured bottlenecks.

6. **Nift adds work without eliminating the control planner.** Hybrid still reads/hashes every source, checks every generated metadata/wrapper, writes the tracked list when changed, launches status, compiles selected records, then launches Nift build. It maintains both the Nift graph and custom content/render/search/app manifests. Native dependency diagnostics and generalized graph handling are plausible benefits, but this particular flat payload graph is already represented by the control keys. Count changed artifacts, planner time, total time and memory independently before attributing value.

7. **Retirement and compatibility coverage remain incomplete.** Removal code does not retire hybrid wrapper, metadata or compiled-intermediate files. This is primarily disk/cache hygiene because tracking excludes removed records. There is no explicit uniqueness/schema validation for corpus slugs before writes. `--content-only` intentionally stops before SSR: serving the same output as static production immediately afterward can expose old HTML, so it must remain a development command. Trusted authored MDX uses `runSync` on function-body code; arbitrary imported MDX modules and strict no-eval CSP are not demonstrated capabilities.

## Verification priorities and adoption decision

The most useful next checks are matched fresh/unchanged/one-Markdown/one-MDX/component/layout/add/remove runs at each corpus size; exact payload/search/SSR content assertions; missing client asset, missing published payload and missing intermediate recovery; preserved-mtime edits; and interrupted publication retry. Validate retired URLs return not found and search removes their entries. App bundle reuse should be established by asset hashes and a retained session note in browser navigation, not only `appRan: false`.

Bounded compilation and SSR, shared runtime behavior and a cache-aware control make this a credible experiment. They also narrow the claim: Nift's added value must come from the native planner/publication boundary itself. Without a measured advantage or existing Nift ecosystem needs, the extra executable, metadata model and publication pass increase ownership cost for an otherwise straightforward content pipeline.

## Final verification addendum

This append supersedes the initial findings where noted; the original text records the earlier review state. I re-read the updated source and saved evidence without running builds, browser checks or mutations.

- **Fixed in source:** native Nift configuration now uses `hash`, retaining `status().stringify()`; the timestamp-semantics mismatch in finding 1 is resolved. Content success keys are committed after publication, and distribution copying also compares prior successful content keys. These changes address the payload retry failure in finding 2. The app key now includes the imported dev plugin, render keys include renderer source/runtime, and search keys include the extracted search-indexer implementation, addressing finding 3.
- **Parent test evidence:** `tools/integration.test.ts` explicitly exercises a year-2000 source mtime, one-document compilation/rendering with app reuse, equal model payloads, literal `@pulse/cli` preservation, and a protected payload destination followed by retry with unchanged success keys after failure. The parent reports this test passed; I inspected its assertions but did not rerun it.
- **Parent browser evidence:** `evaluation/browser-phase2.json` records working interactive tabs/calculator, search results, budget changes and session-note continuity across app/docs navigation for both models, with empty warning arrays in the recorded production checks. This supports the shared-shell claims previously left unverified, within the scope of those recorded interactions.
- **Parent measurements:** `evaluation/results-phase2.json` records 3,000-document fresh builds at 25.20 seconds / 388.97 MiB sampled process-tree peak for hybrid, 23.12 seconds / 402.68 MiB for the optimized control, and 26.93 seconds / 613.71 MiB for the additional native-prerender control. These are measured runs, not repeated distributions or universal limits. Hybrid is about 9% slower than the equivalent optimized control in this fresh run, with about 3% lower sampled peak memory. The native-prerender comparison illustrates a different SSR policy and does not isolate Nift value. Warm measurements are being refreshed after removing an unnecessary forced Nift publication pass; this addendum makes no warm ranking claim.

The remaining structural limitations are the shared global search rebuild/load, existence-only corruption checks, non-atomic publication, unretired hybrid intermediates and the additional graph/orchestration ownership. Payload failure recovery is stronger, but search publication still commits its cache key before copying to the served destination: an interrupted copy to an existing file is not covered by the protected-payload retry test. This narrower search-publication risk is inferred from source, not reproduced.

Nift's specific contribution remains native dependency selection, tracked publication and its dependency metadata/diagnostics. The successful 3,000-document build establishes feasibility; the saved fresh comparison does not establish a compelling advantage over the equivalent hash-planned control. I would still choose the control for a new portal unless the final warm campaign or an existing Nift workflow supplies a concrete benefit that justifies the added integration.
