# Independent TanStack Phase 2 review

Reviewed the integrated prototype's README, Phase 2 notes, app, shared components and build/dev/serve tools, alongside the preserved baseline verdict. This is a source review: no browser, build, benchmark, hydration or navigation execution was performed by this reviewer. The requested final 3,000-document scale is not established by this review.

## Architectural finding

Phase 2 materially answers the baseline's strongest integration objection. Both models now use the same Start Vite plugin, generated file routes, root HTML component, Router links, server functions and React document renderer. `getRouter()` allocates a QueryClient per router and installs the SSR Query integration. Documentation goes through a route loader and the shared MDX component renderer; app data uses Query options and genuine Start server functions. There is no second independently maintained HTML shell in the inspected implementation.

This makes retention of React hydration and client navigation plausible and structurally supported, unlike the hydration-free baseline hybrid. It does not verify hydration success: browser checks must establish that initial document SSR hydrates without mismatch, interactive MDX works immediately, and document-to-document and document-to-app links transition correctly. Static documents carry loader data, including compiled document code, so HTML size and transferred code matter alongside build duration.

Nift's role is now content dependency tracking and payload publication, not page rendering or routing. That is a narrower and cleaner boundary, but also reduces the distinct functionality being purchased with the additional toolchain.

## Strengths verified in source

- The optimized control receives per-document compilation keys, app-stage caching, selective SSR publication, search caching and missing-output recovery. Generic orchestration savings are therefore not automatically credited to Nift.
- Both models compile with the same MDX options, GFM, heading slugs and highlighting, render through the same server bundle interface, and use two bounded compiler workers and two bounded SSR workers. Work is partitioned by documents rather than importing every document into Vite's app graph.
- Content source, document metadata (including previous/next references), compiler source and lockfile feed document keys. Shared components/styles and relevant app sources feed the app key; an app rebuild invalidates all static route renders. Search changes when content keys change. These are meaningful dependencies rather than timing-only shortcuts.
- Server-side document lookup restricts slug characters, checks path containment and treats missing documents as absent. The route converts absence to Router `notFound()`.
- The custom renderer calls the real Start handler and rejects non-success responses. Static HTML publication does not replace the application with a hand-built React-only render approximation.

## Limitations and correctness concerns

1. **Runtime MDX is an explicit architectural tradeoff.** `Document.tsx` executes function-body code with `runSync` on server and browser, using provider components. This preserves interactive MDX without thousands of app imports, but requires trusted authors and a deployment CSP compatible with runtime function evaluation. It also includes the MDX runtime in the client graph and ships document code with route data. This is equal between models and cannot be called a Nift-specific optimization or regression. Arbitrary import/export-heavy authored MDX has not been demonstrated; provider-based examples are the inspected contract.
2. **The publication cache is a manually maintained dependency graph.** `appKey` includes app/shared files and selected configuration, but excludes `tools/render-worker.ts`, `tools/build.ts` and `tools/io.ts`. Changing publication semantics can therefore leave existing HTML accepted as current on an ordinary subsequent build. This is verified by inspecting key construction, not by an executed stale-output reproduction. A supported invalidation/version contract or explicit forced rebuild is necessary after such tool changes.
3. **Output repair has a bounded meaning.** App outputs are checked for existence; document output selection and static HTML rendering likewise use existence checks. Truncated/corrupted existing output is not generally detected. The renderer checks for `<html` and a product string, which is a useful smoke check but cannot certify correct document content or hydration. Reports should distinguish missing-file recovery from integrity checking.
4. **Native prerender is a separate control condition.** The native branch unconditionally invokes Vite and uses Start prerender concurrency four; the optimized publication branch uses two workers. These are legitimate configurations, but not an isolated comparison of framework versus Nift dependency tracking. Report the native control separately, with its rebuild scope and concurrency. Its recorded `rendered` count is requested route count rather than independently counted files.
5. **Dev content updates intentionally reload the page.** The watch bridge runs the shared content build and emits `full-reload`; it is not MDX HMR or document-state preservation. React app HMR and content full reload are separate behaviors. Dev latency requires its own measurement rather than inference from production publication.
6. **Search is a global derived artifact.** Any content-key change rebuilds the whole MiniSearch index, and the browser fetches/deserializes that index. At 3,000 documents this may become a measurable shared cost. No source-only conclusion establishes its magnitude or usability on slower devices.
7. **The serving contract is custom and server-dependent.** Existing HTML/assets are served statically, with Start handling remaining requests, including server functions needed for client navigation. Deploying only the static client directory does not preserve the complete documented experience. Serving a static page also bypasses live SSR, so validation should exercise both published HTML and Start-backed navigation/404 paths.

## Practical assessment and adoption position

The preserved 62-page negative/conditional recommendation should remain historical evidence about its original split architecture. Phase 2 legitimately removes that split; repeating its seamless-shell criticism unchanged would be inaccurate. Conversely, a successful shared shell does not establish a benefit from Nift: the optimized control now supplies most of the same incremental behavior with hashes and a manifest.

For a new TanStack project, my provisional choice remains Start with the optimized content pipeline unless matched measurements and maintenance exercises demonstrate a practical Nift advantage worth its installation, tracking configuration, generated wrappers and extra publication stage. Nift becomes more attractive where its native dependency tracking replaces an otherwise difficult content graph or integrates an existing Nift workflow. Performance superiority, an adoption threshold and production readiness remain open pending the parent's matched benchmarks, browser checks and lifecycle tests.

Useful remaining checks are hydration and interactive MDX after direct static entry; client navigation across document/app routes; removal and renaming; shared component and compiler changes; missing outputs; native/optimized build transitions; and source/toolchain invalidation. These are requested validation targets, not completed tests.
